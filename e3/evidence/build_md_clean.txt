#
# 场景：fixtures/md-rd（接 build_md_unbuilt.txt）
# 命题：与 build_md_unbuilt.txt 同样改 config.h 的 VALUE 为 2，
#      但本次走 `make clean && make`，强制全部重建，app 应输出新 VALUE 2。
#
# 数据来源：work/20260920-135225/md-rd.commands.json + md-rd.observations.json
# 时间：2026-09-20T13:52:26

[step 1] clean：删除 main.o 与 app，强制 main.c 重编
  $ rm -f main.o app
  stdout: rm -f main.o app  ->  removed: main.o
  exit_code: 0

[step 2] 全量重建
  $ mingw32-make app
  stdout:
    gcc -O0 -Wall -c main.c -o main.o
    gcc main.o -o app
  exit_code: 0
  → 注意：与 build_md_unbuilt.txt 的 step 3 不同，stdout 里**有** `gcc -c main.c -o main.o`，
    因为 main.o 不存在，Make 走"全量重建"分支，触发 cc 编译。

[step 3] 运行 app（clean build 拾取新 VALUE）
  $ ./app
  stdout: 2
  exit_code: 0
  → 期望 = 2，实际 = 2，**PASS** ✅

## 结论

同一个被遗漏的 config.h 依赖（MISSING），用两种构建方式得到两种结果：
- 普通 make（漏重建）→ 旧 VALUE 1 → 见 build_md_unbuilt.txt
- clean make（全量重建）→ 新 VALUE 2 → 见本文件

这正是 BuildChecker 需要诊断的核心场景：
**"普通 make 没报错"≠"构建正确"**——MD 不影响 clean build，只影响增量构建的可见性。
BuildChecker 应该报 MISSING 让用户知道"config.h 是隐式依赖，下次改它 make 不会重编"。

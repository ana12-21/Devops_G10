### 四个提交与结果

|---|---|---|---|---|---|

### 各步判定

- **C1 body change**：`main.c` 中 `VALUE+helper()` 改为 `VALUE+helper()+0`。`C1-build.log` 显示 `gcc -O0 -c main.c -o main.o` 和链接，**helper.o 未重编**。普通表达式变化意味着 Make 仍会执行部分编译，但依赖分析可以完全复用——`C1_REUSE_PASS`。
- **C2 include change**：`main.c` 顶部加 `#include "extra.h"`，构建仍成功（`C2-build.log` 同 C1）。但**构建成功不等于依赖无误**：`extra.h` 已进入真实读取集合，而 Make 声明未跟随。分析得到 `refreshed={'main.o','helper.o'}`、`added=[[MISSING, main.o, extra.h]]`，原 MD config.h 与 RD unused.h 仍在——`C2_REFRESH_PASS`。
- **C3 repair declarations**：`main.o: main.c unused.h` → `main.o: main.c unused.h config.h extra.h`。配方与 `CFLAGS` 未动，因此 `key` 相等，实际图复用；但声明图重新解析，`resolved` 恰为两条 MD，RD unused.h 保留——`C3_RESOLVED_PASS`。

C3 是本实验的核心观察：**同一份真实图，配不同的声明图，产出的 findings 完全不同**。这说明实际图与声明图必须分开维护，复用实际图不等于复用结论。

解读（不做美化）：

1. **复用确实带来约 5.8 倍加速**（`unchanged`/`body`/`declaration`），因为跳过了两次 `gcc -MM` 子进程。
2. **刷新场景加速比 ≈ 1.0**（`include`/`flags`/`header`），因为增量和全量做的是同一批 `gcc -MM`，前者没有省下任何工作。这是保守刷新策略的**直接代价**：配置变了就全刷，收益归零。

4. `declaration` 第 1 次 0.005531 s 也有类似的冷启动现象，其余 4 次稳定在 0.0017 s。
5. 计时口径：包含 `scan` 内的 Git 调用、编译器版本探测、Makefile 解析与 `gcc -MM`；**不包含完整 clean build 耗时**。因此这里的数字不能与论文的加速倍数直接对比——样例太小，绝对值都在 10 ms 量级。

## 论文机制对应、教学简化与扩展计划

对应论文的「基于历史图复用未变化输入的增量分析」：一次真实构建（`strace -ff` + `make -p`）产出对象级依赖基线；后续提交只需比对缓存身份，身份未变就复用旧图，避免重复付出系统调用跟踪代价。E8 建立基线，E9 演示逐提交更新与 MD 的新增/消除，E10 用 30 行矩阵量化一致性与代价。

教学简化：

1. 缓存身份是「预处理指令行 + 配方行 + CFLAGS + 编译器版本」的粗粒度组合，配置与身份绑成同一个 `key`。真实系统还要考虑命令行宏差异、条件编译分支、编译器内部头文件版本。
2. 失效粒度是全局的：一个 `.h` 变化让所有目标 refresh，没有 per-target 精细失效。E10 的 `flags`/`header` 场景加速比 ≈1.0 就是这个代价的量化结果。
3. 依赖采集走 `gcc -MM`，`CFLAGS` 只接受 `-O0`/`-O1`/`-O0 -DMODE=1`；Makefile 只支持显式规则加简单变量展开（最多 8 层），出现 `%`、`|`、未定义变量直接 `UNSUPPORTED_DECLARATION`。

扩展计划：把 `key` 细化为 per-target 的「该目标翻译单元闭包内的头文件指令集合」，让 `helper.o` 在只改 `config.h` 时仍可复用；再用 E10 同样的 30 行方法验证精细失效没有漏边。

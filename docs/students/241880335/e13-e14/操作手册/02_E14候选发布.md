## 2. 部署与故障观察

旧 `labs/e11e12/environment/compose.yaml` 只定义 BuildChecker；旧 `run_e11e12.py` 在一个容器里串行运行四项能力。本包新增 `03_实验包/compose.yaml`、`service.py` 和 `orchestrate.py`。导入个人仓库 `labs/e13e14/` 后，用四个容器分别运行 BuildChecker、EChecker、DRAFT、MDFixer；编排入口经各服务 HTTP 接口传递阶段数据。它们共用已构建的 E11–E12 教学镜像和工作目录，只有 DRAFT 挂载 Docker socket。端口仅在服务器 `127.0.0.1` 上监听。

在**隔离测试仓库**运行，先确认本仓库已执行 E11–E12 的 `build`、`prepare`，并把 `E14_IMAGE` 改为本人的实际镜像标签。`docker compose config` 通过后再启动：

```bash
cd /绝对路径/个人仓库
python3 -m py_compile labs/e13e14/service.py labs/e13e14/orchestrate.py
E14_ROOT=$PWD E14_IMAGE=course-e11e12:替换为本人学号 docker compose -f labs/e13e14/compose.yaml -p e14-替换为本人学号 config --quiet
E14_ROOT=$PWD E14_IMAGE=course-e11e12:替换为本人学号 docker compose -f labs/e13e14/compose.yaml -p e14-替换为本人学号 up -d
E14_ROOT=$PWD E14_IMAGE=course-e11e12:替换为本人学号 docker compose -f labs/e13e14/compose.yaml -p e14-替换为本人学号 ps
```

四项状态应为 `healthy`。一键入口的请求 JSON 仍沿用 E11–E12 `e12.json` 字段；项目、候选文件位于本仓库 `data/`，输出必须是新的 `work/` 子目录。先用固定样例，再用配对双方的实际项目请求：

```bash
python3 labs/e13e14/orchestrate.py --request data/integration-sample/e12.json --out work/e14-compose-sample-01 > work/e14-compose-sample-console.log 2>&1
printf 'COMPOSE_SAMPLE_EXIT=%s\n' "$?"
cat work/e14-compose-sample-01/result.json
```

核对五阶段 `draft → full-check → incremental-check → repair → recheck`，同一 job_id/trace_id，报告传输 SHA、补丁接受、最终无 `MISSING`，以及 `result.json` 中每个产物的字节哈希。用 `docker compose ... logs` 分别确认四容器确实处理了本轮请求；日志应有角色、job_id、trace_id、状态、耗时和失败错误码。仅看到四个容器 healthy 不能代替五阶段运行。运行日志还须单独使用 `scan_runtime_logs.py` 检查。

教师安排一次**受控**故障注入，例如在复制的请求中把 `build_timeout` 设置为 `0.01`，用全新输出目录运行并确认 DRAFT 超时、外层失败，然后恢复原时限在另一个新目录重试成功。检查两次 job_id/trace_id、失败任务残留进程和容器，并保留四服务日志。不要停止共享 Docker 服务或清理其他组容器。

彩排完成后按本组安排执行 `docker compose ... down`，只关闭本次指定的 Compose 项目。发布清单需区分“教学样例四容器通过”和“实际组项目四容器通过”。

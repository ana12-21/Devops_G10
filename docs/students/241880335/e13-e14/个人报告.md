## 几处判断

1. 没有把本机代跑写成跨组联调。B 组缺席时最省事的做法是把双向结果都记成「C1 通过」。但 C1 的合格观察里明确包含「B 校验并消费 A 当次报告」，这一条只有 B 组在他们仓库里跑才算。所以 C1 拆成两半写：A 侧检测（真跑了，记为通过）、B 侧消费（未执行）。C4 和 C5 同理，一条都没有代做。

2. 先记录 `UNSUPPORTED_PROJECT` 再谈适配。手册写过「不符合该范围时应先记录 `UNSUPPORTED_PROJECT`，扩展适配和测试后再评价算法正确性」。所以 B 组项目先原样跑出拒绝，再在隔离副本里改四项，每一步都写进 `ADAPTATION.md`，并且单独列明「哪些没改」。这样适配过程不会把被测缺陷掩盖掉。

3. 遇到 403 不碰教师原件。三个项目和一等样例都被 tuna 的 403 挡住。我没有去改教师发的 `candidate.Dockerfile`，而是另存 `candidate-local-mirror.Dockerfile`（差一行，前后 SHA 都记录），原件是什么、我改了什么、为什么改，三件事都能复核。

4. 不改检查来换通过。`validate()` 里写死 `VALUE` 那个问题，最省事的解法是改 `validate()` 或改 B 组的 `main.c`。两条路都会让门禁失去意义：前者放松了检查，后者改掉了被考察的对象。所以选择记录成适配边界。

5. 候选状态如实写「候选待发布」。手册写明「若任何一项未完成，将状态写为“候选待发布”，保留证据继续修复，不虚构 RC 已发布」。`git tag --list 'v0.9-rc'` 是空的，也没推远端、没开 PR。

## 收获

这轮最直接的体会是，门禁能挡住什么，比它能放行什么更重要。中间有三处地方眼看着可以「让它过」：改 `validate()`、改 B 组的 `main.c`、把 C1 写成双向通过。三处都放过去，报告会好看很多，但 E13 想训练的独立验证和缺陷闭环就没有了。最后的选择是把边界写清楚，没做的标成没做。

环境问题我也记成了缺陷，没有绕过去。tuna 403 表面上像「跑不动」，但它本身可以复现：有 curl 状态码、有 apt 原始报错、有改动前后的 SHA。写进缺陷清单之后，别的组遇到同样问题可以直接用这个结论。

失败证据比成功证据更能说明系统的可靠性。C7 的隔离结论、E14 超时注入后「无残留 docker build 客户端」的检查、三次 E14 失败的目录都原样留着，这些才说明失败不会污染下一个任务。

多角色部署会把单进程时被掩盖的问题暴露出来。拆成四个容器之后，报告传递的哈希校验、`Dockerfile.broken` 的存在性、候选指令序列的约束，才一个接一个地冒出来。

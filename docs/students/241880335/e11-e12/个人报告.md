## E11 轨道集成

### 上游输出 → 下游输入 → 字段映射

A 组的集成链路是 **BuildChecker（E5–E10 的 `full_check`）→ EChecker（`labs/e8e10/lab.py` 的 `scan`）**，两边的产物形状并不一致，`labs/e11e12/pipeline.py` 负责把它们接起来。

|上游产出|下游消费|形状差异|处理方式|
|---|---|---|---|
|`baseline-full/actual-graph.json`（`full_check` 观测全量构建）|`scan()` 的 `old` 参数（要求 `actual` 形如 `{目标: [依赖列表]}`）|BuildChecker 输出的是**边列表** `[{target, dependency}]`，且包含链接目标 `app`|投影到 `main.o`/`helper.o` 两个对象目标后写入 `baseline-cache.json`|
|`target-full/findings.json`（全量观测）|与增量报告做一致性对照|同样含 `app`|`pipeline.normalized()` 过滤到对象目标|
|`incremental-report.json`（`scan` 输出，`schema_version=e8e10-1`）|封装为 `incremental-check.json`（`schema_version=e11e12-1`）|schema 与字段不同|`stage()` 包一层 envelope：`job_id`/`trace_id`/`kind`/`commit`/`status`/`data`/`artifacts`|
|计算得出的 `findings`|envelope 的 `data` 字段|—|原样放入|

版本与字段：所有 envelope 统一为 `schema_version = e11e12-1`，必填字段 `job_id`、`trace_id`、`kind`、`commit`、`status`、`data`、`artifacts`。`artifacts` 里每项是 `{uri, sha256, bytes}`，`uri` 形如 `artifact://<job_id>/<相对路径>`。

**基线必须来自真实执行，不能只靠 `gcc -MM`。** `pipeline.execute()` 里有这段：

```python
edges = json.loads((out/'baseline-full/actual-graph.json').read_text())
projected = {t: sorted({e['dependency'] for e in edges if e['target'] == t}) for t in ('main.o','helper.o')}
if projected != old['actual']:
    raise Failure('GRAPH_MISMATCH', 'BuildChecker baseline differs from GCC observations')
old['actual'] = projected
```

先跑真实 `strace`，投影后与 `gcc -MM` 交叉核对，不一致直接 `GRAPH_MISMATCH`。这样基线既来自真实执行，又不会因为真实图出错而无人发现。

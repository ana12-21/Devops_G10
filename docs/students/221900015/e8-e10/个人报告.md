## A组：机制与数据

**历史图来源**：`baseline.json` 不是自造的，而是把 BuildChecker 在 strace 下采集的真实 `actual-graph.json` 投影到 `main.o`/`helper.o` 两个对象目标（`baseline_source` 字段有记录），耗时 0.01883s；投影后与 `gcc -MM` 的声明集合做相等断言，保证基线不是空图。

**变化类型与复用/刷新**：失效键 `key` 由全部 `.c/.h` 的预处理指令、Makefile 配方行、`CFLAGS`、编译器版本四部分构成。E9 中 C1 只改函数体，键不变 → 两个目标全部复用（0.00207s）；C2 增加 include，键变化 → 两个目标全部重建图（0.01083s）；C3 只改 Makefile 声明，键不变 → 图复用，但 `findings` 由声明重新计算。

**发现新增/消除**：C2 新增 `MISSING extra.h`；C3 同时消除 `MISSING config.h` 与 `MISSING extra.h`，并保留 `REDUNDANT unused.h`（该头文件被声明但从未被包含）。这说明复用图不等于复用检查结论，`resolved/added` 必须按当前声明重算差集。

**全量核对结果**：`matrix/gate.json` 为 `{"track":"A","passed":true,"rows":30}`；30 行 CSV 的 `equal` 全为 True，即增量路径与全量路径在 actual、declared、findings 三个集合上逐行相等。最终 `matrix/final-buildchecker/` 是用真实 BuildChecker 对末态工程的复核（`MISSING config.h`、`MISSING extra.h`、`REDUNDANT unused.h`），与增量结果一致。

**结论边界**：加速只发生在“依赖结构未变”的三类（unchanged/body/declaration）；只要 include 指令、头文件内容或编译参数变化，本实现选择全量刷新，增量与全量同速。这是有意的保守设计，避免漏检新增头文件。

- 输入：`config.h` 顶部增加 `#include "extra.h"`，提交后增量扫描。

## 论文机制对应、教学简化与扩展计划

对应 EChecker 的两条主张：一是用真实构建轨迹（strace 记录的 open/execve）而不是头文件猜测来获得依赖图；二是把上一次的图当作缓存，在配置指纹不变时直接复用、变化时重建。本实验的简化在于：只处理显式 Makefile 的 C 项目、只投影对象级依赖、不做并发构建的进程归并；失效判定是全局指纹而非论文中的配置项级增量比较。

扩展计划：把全局指纹细化为“目标级指纹 + 头文件反向依赖闭包”，在保证 `incremental==full` 的前提下让 header 变更只刷新真正包含它的目标；同时把 `key` 的编译器探测结果做成可注入参数，便于跨机器复现。

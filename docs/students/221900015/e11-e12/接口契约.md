# e11e12-1 接口契约（221900015 复核与补充）

| 接口 | 请求/响应 | 状态码 |
|---|---|---|
| POST /v1/jobs | `idempotency_key`、`input`(mode/repo/base/target/candidate 等)；返回 job_id/status | 202；输入错误 400；幂等冲突 409 |
| GET /v1/jobs/{job_id} | 任务状态、trace_id、error | 200；不存在 404 |
| GET /v1/jobs/{job_id}/artifacts | 阶段清单与 artifact URI/SHA256 | 200；结果未生成 409 |
| GET /v1/jobs/{job_id}/files/{相对路径} | 产物文件与 `X-Content-SHA256` | 200；不存在或越界 404 |

任务状态：QUEUED、RUNNING、SUCCEEDED、FAILED、TIMED_OUT。输出 envelope 的 `schema_version/job_id/trace_id/kind/commit/status/data/artifacts` 为消费者依据。`artifact://job编号/相对路径` 由文件接口解析，MD 消费需核对目标 commit 与内容哈希；基线与目标提交不同是正常的，必须分别记录。

真实项目适配时把仓库与候选准备到 API 服务器 `data/` 下，服务只开放到本地，A/B 通过 SSH 转发访问。

## 本人补充（按实测行为写死，供评审对照）

1. **校验顺序**：`mode` 合法性 → `repo` 存在且位于 `data/` 下（否则 400 `repo must be under /course/data`）→ base/target 快照 → （e11-b/e12）candidate 构建与输出比对 → fixed-md/full-check 校验 → 补丁 → validate → 复检。任何一步失败都会写 `result.json` 的 `status/error`，不会留下“看起来成功”的空阶段清单。
2. **幂等键**：同 key 同 `request_hash` 返回原 job（202，状态可能是 QUEUED/RUNNING/SUCCEEDED）；同 key 不同 `request_hash` 返回 409 `IDEMPOTENCY_CONFLICT`；重启后用同一 key 重提，旧 job 若已完成仍复用，未完成则必须换新 key。
3. **重启语义**：进程重启只把 RUNNING/QUEUED 收敛为 `FAILED / SERVER_RESTARTED`，不会自动续跑；已完成任务从 `state.json` 恢复（`work/api-221900015/after-restart-old.json`）。
4. **产物哈希**：`files` 接口返回的 `X-Content-SHA256`、本地重算值、`artifacts[].sha256` 三者必须相等；实测 `candidate.patch` 为 `88074f66…cb2af`，274 B。
5. **报告新鲜度**：`check_envelope` 与 `patch()` 双层校验 `commit`；旧报告返回 `STALE_REPORT`，且目标 `Makefile` 字节不变。
6. **依赖路径**：`../`、绝对路径、含空格或非法字符的依赖在写盘前抛 `UNSAFE_PATH`（本人用例覆盖三种）。
7. **容器内路径**：请求里所有路径按 `/course/...` 解析，宿主绝对路径会得到 `Repository missing`（`work/e11-b-macro-00-pathbug` 是反例，正式运行用 `work/e11-b-macro-01`）。

# 版本与变更说明

> E2 交付项：说明哪些变更是**兼容的**、哪些是**破坏性的**，以及**共享 Schema 如何同步**。
> 责任方：A/B 共同。**需与 B10 确认**（任一方改契约都必须走本流程）。

## 1. 版本号在哪里

| 位置 | 字段 | 当前值 |
|------|------|--------|
| `contracts/task.schema.json` | `schema_version`（`const`） | `1.0.0` |
| 每个任务文档（请求/响应） | `schema_version`（必填） | `1.0.0` |

版本号是**整个契约集合**的版本，不是单个文件的版本。四类任务
（`DRAFT` / `FULL_CHECK` / `INCREMENTAL_CHECK` / `REPAIR`）共用同一个版本号。

## 2. 版本号策略

采用 `MAJOR.MINOR.PATCH` 三段式：

| 段位 | 何时递增 | 示例 |
|------|----------|------|
| `MAJOR` | 出现任何**破坏性变更** | `1.0.0` → `2.0.0` |
| `MINOR` | 新增**可选**字段或可选枚举值，旧消费者可忽略 | `1.0.0` → `1.1.0` |
| `PATCH` | 仅修正文档措辞、样例笔误，**载荷结构不变** | `1.0.0` → `1.0.1` |

> 判定口诀：**旧文档还能不能被新消费者接受？新文档还能不能被旧消费者接受？**
> 两个都是"能"，就是兼容变更；有一个"不能"，就是破坏性变更。

## 3. 兼容 vs 破坏性 判定表

### 3.1 兼容变更（可只升 `MINOR` / `PATCH`）

| 变更 | 为什么兼容 | 前置条件 |
|------|------------|----------|
| 新增**可选**字段 | 旧文档不带该字段仍合法 | 消费者**必须允许**未知/缺失字段 |
| 新增**可选**枚举值 | 旧文档不会用到新值 | 消费者对未知枚举值需降级而非报错 |
| 补充 `detail` 内的上下文字段 | `detail` 本身是自由结构 | — |
| 新增产物 `type` | 消费者按 `type` 过滤 | 需双方登记 |
| 文档措辞、样例注释修正 | 不影响载荷 | — |

### 3.2 破坏性变更（必须升 `MAJOR` 并记录）

| 变更 | 为什么不兼容 |
|------|--------------|
| **删除**字段 | 依赖该字段的消费者直接失败 |
| **改名**字段 | 等同删除 + 新增，消费者读不到原字段 |
| **改变字段语义**（名字不变、含义变了）<br>例：`configuration_id` 从"编译配置"改为"容器配置" | 最危险 —— 消费者不报错但结果错误 |
| **改变状态枚举**<br>例：删掉 `TIMED_OUT`、新增 `SUBOPTIMAL` | 状态机分支失效，`switch` 落空 |
| 把**可选**字段改为**必填** | 旧的合法文档突然全部非法 |
| **严格 Schema 拒绝新增字段**<br>例：`additionalProperties: false` + 未登记字段 | 阻塞了兼容变更的演进路径 |
| 改变 `schema_version` 的 `const` 校验方式 | 协商机制本身失效 |

> ⚠️ 注意最后一条的反面：**`additionalProperties: false` 本身不是破坏性变更，
> 但它把"新增可选字段"这条路也堵死了**。因此若采用严格模式，
> 每次新增字段都必须与对方同步发布新 Schema，属于**耦合升级**，
> 必须按第 5 节的流程走。

## 5. 共享 Schema 同步流程

A、B 两组共用一份 `task.schema.json`。任何一方改动**必须**走完以下步骤，
否则会出现"我这能过、他那不过"的接口事故。

```
第 1 步  提议        任一方开 Issue，说明：改什么 / 为什么 / 判定为兼容还是破坏
                        ↓
第 2 步  判定        双方按第 3 节表格共同判定变更类型
                     · 兼容   → 继续
                     · 破坏   → 必须同时商定迁移方案与截止时间
                        ↓
第 3 步  改 Schema   在分支上修改 contracts/task.schema.json
                     · 兼容   → schema_version 升 MINOR
                     · 破坏   → schema_version 升 MAJOR
                        ↓
第 4 步  同步样例    ★ 最容易漏的一步 ★
                     把所有受影响的 *.req.json / *.res.json / *.sample.json
                     一次性改齐，不允许只改一部分
                        ↓
第 5 步  跑校验      python e2/scripts/validate.py --all
                     退出码必须为 0
                        ↓
第 6 步  PR + 复核   PR 描述中写明：变更号（如 C-03 / D-01）、判定结论、
                     受影响文件清单、验证命令与结果
                     对方组至少 1 人在 PR 上明确回复"确认"，方可合并
                        ↓
第 7 步  记录        在本文档第 4.2 节追加一行变更记录
                     破坏性变更另在 `docs/ADR-*.md` 补一条决策记录
```

### 同步检查清单（每次改契约都过一遍）

- [ ] 变更已判定为兼容 / 破坏，并在 PR 描述中写明
- [ ] `schema_version` 已按判定升位
- [ ] **所有**受影响样例已同步修改（包括 `negative/` 与 `errors/`）
- [ ] `validate.py --all` 退出码为 0
- [ ] 本文档第 4.2 节已追加变更记录
- [ ] 对方组已在 PR 上确认

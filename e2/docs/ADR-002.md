# ADR-002: 将系统执行错误与检测发现分离

- **Status**: Accepted
- **Date**: 2026-09-20
- **Authors**: A10 组
- **Scope**: A 组（BuildChecker / EChecker）；涉及共同契约，**需与 B10 确认**

## Context

BuildChecker / EChecker 的任务产出天然有两类"坏消息"：

1. **平台或工具自身出了问题**——镜像构建失败、任务超时、分析器崩溃。此时任务**没有**产出可信结论。
2. **工具正常跑完，但发现了依赖问题**——`MISSING`（实际需要但构建文件未声明）、`REDUNDANT`（声明了但本配置未用）。此时任务是**成功**的，发现就是它要交付的成果。

如果两类信息共用一个字段，会立刻产生三个问题：

- **消费者无法判断任务是否可信**。B10 的 MDFixer 拿到一份含 `MISSING` 的报告时，必须能确认"这份报告来自一次成功执行"，而不是"分析器崩了一半吐出来的残次品"。
- **状态语义被污染**。若把 `MISSING` 当作错误，那么一次成功的检测会因为"发现问题"而被标成 `FAILED`，与 E2 规范中 `SUCCEEDED` 的定义冲突。
- **重试策略无法定向**。`EXEC_4002`（超时可重试）与 `MISSING`（重试一万次结果一样）需要完全不同的处理方式。

课程规范第 3 条明确要求：系统错误（`ENV_3002` / `EXEC_4002` / `ANALYSIS_5001`）写入 `job.error`；正常分析发现（`MISSING` / `REDUNDANT`）写入 `ERROR_REPORT` 的 `findings`，且检测正常完成时状态可为 `SUCCEEDED`。

## Decision

**两类信息物理分离，且互斥。**

### 1. 载荷分离

| 类别 | 承载字段 | 对应状态 | 示例 |
|------|----------|----------|------|
| 系统执行错误 | `job.error` | `FAILED` / `TIMED_OUT` | `ENV_3002`、`EXEC_4002`、`ANALYSIS_5001` |
| 检测发现 | `output.findings` 或产物 `ERROR_REPORT.findings` | `SUCCEEDED` | `MISSING`、`REDUNDANT` |

### 2. 错误码与发现码不共用命名空间

- 错误码格式：`{域}_{四位}`，首位分域 —— `1=Schema`、`2=Baseline`、`3=Env`、`4=Exec`、`5=Analysis`、`6=NotFound`、`7=Conflict`。
- 发现码固定只有 `MISSING` / `REDUNDANT` 两个值，与错误码前缀体系完全不重叠。

### 3. 互斥不变量（可在校验脚本中断言）

```
SUCCEEDED + output.findings   → 合法
FAILED    + job.error         → 合法
job.error + output.findings   → 违例（同一 Job 只能写一处）
SUCCEEDED + job.error         → 违例
QUEUED    + output            → 违例（尚未开始执行）
```

已落盘反例：`contracts/negative/error_and_findings.res.json`。
正面样例：`contracts/md_report.sample.json`（有 findings、无 error、状态 `SUCCEEDED`）、`contracts/analysis_err.res.json`（有 error、无 findings、状态 `FAILED`）。

## Alternatives

### 方案 B：合并到单个 `job.error` 字段，用子类型区分

- ✅ 结构简单，解析路径统一
- ❌ 破坏 `status` 语义：成功检测出问题会被读成失败
- ❌ B 组必须解释子类型才能判断报告是否可信，耦合度反而升高
- ❌ 与课程规范冲突

### 方案 C：用 `SUBOPTIMAL` 三态表达"成功但有发现"

即 `SUCCEEDED` / `SUBOPTIMAL` / `FAILED`。

- ✅ 只需看 `status` 就能区分
- ❌ 引入新枚举值，**属破坏性变更**，必须与 B10 同步改 Schema 并重新协商
- ❌ 与规范给定的六态状态机（`QUEUED / RUNNING / SUCCEEDED / FAILED / TIMED_OUT / CANCELLED`）不一致
- ❌ "有发现"与"任务状态"本就是两个正交维度，硬合成一维会在将来出现"成功但发现很多"时再次失效

### 方案 D：用 HTTP 状态码表达

- ✅ 无需改载荷结构
- ❌ 异步模式下真正的结论在 `GET /v1/jobs/{job_id}` 里，HTTP 状态码只描述"查询是否成功"，无法描述"任务结论"
- ❌ 5xx 会让客户端重试，而 `MISSING` 重试没有意义

## Consequences

### 正面

- **消费者可独立判断可信度**：B10 只要看到 `status=SUCCEEDED` 且无 `job.error`，就确定这份 `findings` 来自一次完整执行。
- **重试策略可定向**：`EXEC_4002` 可重试，`MISSING` 不重试。
- **状态机保持六态**，不引入破坏性枚举变更。
- **命名空间不冲突**：错误码体系与发现码体系各自独立演进。

### 代价

- `job.error` 与 `output.findings` 的互斥必须**被显式校验**，不能靠约定；否则迟早有人两个都写。→ 由 `scripts/validate.py` 断言 + `contracts/negative/` 反例兜底。
- 消费者需要理解"`SUCCEEDED` 不等于没问题"，文档必须把这一点讲清楚。→ 由 `contracts/negative/README.md` 的"MD ≠ 工具执行失败"一节承载。
- `ERROR_REPORT` 成为独立产物类型，比"把发现塞进响应"多一层 URI 间接寻址。→ 换来的好处是报告可被 B 组独立取用、可存档、可用 `sha256` 核验。

### 遗留

- `ERROR_REPORT` 中 `finding.commit` / `location` / `evidence_uri` 是否全部提升为**必填**，需与 B10 确认（当前 `practice_log.md` 已倾向必填，但既有样例尚未统一）。**需与 B 组确认**。
